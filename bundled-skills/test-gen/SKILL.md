# 单元测试生成

## 步骤

1. **读被测代码**：理解输入域、副作用、错误路径。找到仓库既有测试风格
   （框架、断言库、命名、目录约定）并严格跟随——测试代码比业务代码更需要一致性。
2. **设计用例清单**（先列后写）：
   - 正常路径（1-2 个代表输入）
   - 边界：空/零/最大值/单元素/Unicode/超长
   - 错误路径：每个 `Err`/异常分支至少一个
   - 回归：能想到的历史 bug 形态
3. **编写**：
   - 测试名描述行为而非方法：`rejects_negative_amount` 而非 `test_1`。
   - 一个测试一个断言主题；Arrange-Act-Assert 三段清晰。
   - 不测私有实现细节；通过公共 API 驱动。
   - 需要网络/时间/随机数时用注入或 mock，禁止真实外呼。
4. **运行验证**：执行仓库测试命令确认全绿；失败自己修到通过（除非用户另有要求）。
5. **汇报**：列出新增用例数与覆盖的场景类型。

## 红线

- 不要为了让测试通过而修改业务代码语义；发现疑似 bug 先报告。
- 不引入新的重型测试框架依赖，除非用户同意。
